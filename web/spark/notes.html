Working notes: the earlier design

Kept for reference. These notes come from before the final slide. The diagram on the dashboard is the source of truth now, and plan.md is how it gets built. Where anything below disagrees with them, the diagram wins.

Version 2 of the demo. The channel emulator moves off the RFSoC and into software on one DGX Spark: OCUDU DUs and OAI UEs exchange IQ over ZMQ, and a Sionna PHY channel runs on the GPU in between. No FPGA build, tool licence or bitstream is involved. This is a design: nothing below has been built or run yet, and every figure is either from a cited source or marked as an estimate.

System

Where each part runs

The one-page diagram is the brief. In words, end to end:

1OCUDU CU and two DUsArm CPU One CU, two DUs, one cell each. Each DU uses the stock zmq radio driver instead of a USRP.
2IQ brokerArm CPU A Python process that sits in every ZMQ link between a DU and its UE. It answers each pull with exactly the samples asked for.
3Channel emulatorGPU Sionna PHY on the Blackwell GPU. It filters each block, adds noise and bias, and hands it back through unified memory.
4Live taps publisherGPU Publishes new channel taps on PUB tcp://127.0.0.1:5566; the emulator swaps them in between slots.
5OAI UEsUE side Two nr-uesoftmodem instances, one per cell, each in its own network namespace (ue1, ue2).
6UE brokerUE side A script that joins the two UE interfaces to the multipath TCP client, one subflow per UE.
Sockets

The ZMQ links

Every IQ link is ZMQ request/reply: the reader asks, the writer answers. The DU side is read from the OCUDU source (lib/radio/zmq/). Port numbers are the TOSSI reference set for one gNB; the second DU's pair is not chosen yet.

Live taps message

Kept identical to the TOSSI format so its tooling stays usable: little-endian magic=0x4F434952, version=1, sequence, num_snapshots, num_tx_ant, num_rx_ant, num_taps, loop (uint32), then fs_hz and snapshot_dt_s (double). Limits: 64 taps, 4 antennas a side; fs_hz must equal the stream rate. A malformed update is dropped and the last good taps stay.

Loop

The emulator loop, every 0.5 ms slot

Sionna 2.2.0; PHY is PyTorch. All calls are in sionna.phy.channel.

StepCallWhat it does
1 · PullREQ30,720 IQ samples per stream from the DU (DL) or UE (UL)
DecisionSUB :5566new taps waiting? Yes: swap them in and go to step 4
2 · Tapstr38901.TDL(model, delay_spread, carrier_frequency, min_speed, max_speed)3GPP multipath model; called with (batch_size, num_time_steps, sampling_frequency), returns a, tau
3 · Samplecir_to_time_channel(bandwidth, a, tau, l_min, l_max)paths to discrete taps by sinc interpolation; span from time_lag_discrete_time_channel
4 · FilterApplyTimeChannel(num_time_samples, l_tot)time-varying convolution on the GPU; output is N + l_tot − 1, so the tail carries into the next slot
5 · NoiseAWGN()noise at the set power, then the I/Q bias
6 · ReturnREPexactly 30,720 samples, so the link stays in step

The v1 equation, y[n] = e^{jφ}·x[n − d] + b, is the one-path case: a = e^{jφ}, tau = d / fs through the same cir_to_time_channel, bias added after.

OFDM

Orthogonal Frequency-Division Multiplexing (OFDM)

Each subcarrier carries one QAM symbol; an IFFT sums all N into one OFDM symbol. Symbols fill the grid frequency-first, S0 … SN−1 down OFDM symbol 0, then SN onward; N = 12 in the figure is an example. After the IFFT and cyclic prefix in the DU (downlink) or UE (uplink), one slot is one 30,720-sample block on each ZMQ stream. The emulator's plain pipe only ever sees those time samples.

Sionna RT

Sionna RT in the loop, and where the FFT goes

IQ from the server at t₀ is transformed to subcarriers, each subcarrier symbol is multiplied by the channel Hₖ from Sionna RT, and the result reaches the UE at tₙ.

Key: accent outline, Sionna RT and the product it feeds · grey bar, a ZMQ socket.

FFT placement

On the IQ path, before the channel is applied: IQ → FFT → Hₖ · Sₖ → IFFT.

Outside Sionna RT. Sionna RT never receives IQ samples; it returns Hₖ at the subcarrier frequencies (Paths.cfr). The FFT is OFDMDemodulator in Sionna PHY.

Not settled by the whiteboard

An arc over the FFT box runs to a second “Sionna RT” label, so the board may be grouping the FFT inside Sionna RT. The IFFT is not drawn; tₙ implies it. “Outside” follows the Sionna RT API, which has no call that takes IQ.

Load estimate: 4 streams × 61.44 Msps × 8 B ≈ 2 GB/s, under 1% of memory bandwidth; about 24 M complex multiply-adds per slot across all streams. Launch and hand-off time, not arithmetic, should set the latency. Unified memory does not make PyTorch zero-copy by default; that has to be measured.
